# AgentPass 프로젝트 계획서

> 작성일: 2026-10-14 · 상태: Draft v0.1 · 작성: Claude (사용자 위임 하에 주요 의사결정 포함)

## 1. 한 줄 정의

**AgentPass** — AI 에이전트가 사용자를 대신해 상거래를 수행할 때 필요한
**① 에이전트 신원 확인(Know Your Agent), ② 사용자 위임(Mandate), ③ 거래 시점 검증**을
표준 기반으로 제공하는 "에이전트 커머스용 인증·인가 인프라"(Identity & Delegation Layer).

## 2. 왜 지금인가 (문제 정의)

기존 커머스 인증은 "화면 앞에 사람이 있다"를 전제로 설계되었다.

| 기존 전제 | 에이전트 커머스에서의 현실 |
|---|---|
| 로그인 = 사람이 비밀번호/패스키 입력 | 에이전트가 API/브라우저로 접근, 사람은 부재 |
| 봇 = 악성 (CAPTCHA, 봇 차단) | 선량한 봇(구매 대행 에이전트)과 악성 봇을 구분해야 함 |
| 결제 승인 = 사람이 그 자리에서 클릭 | "5만원 이하 생필품은 알아서 사줘" 같은 **사전 위임** |
| 분쟁 = "내가 안 샀다" | "에이전트가 내 의도와 다르게 샀다" — 의도 증빙 필요 |
| 계정 공유 = 약관 위반 | 에이전트에 비밀번호를 넘기는 위험한 관행이 확산 중 |

이 간극 때문에 머천트는 (a) 에이전트를 막아 매출 기회를 잃거나 (b) 무방비로 허용해 사기·차지백
위험을 떠안는다. 사용자는 (c) 자격증명을 에이전트에 통째로 넘기는 위험을 감수한다.

## 3. 목표 / 비목표

### 목표 (v1)
1. **에이전트 신원**: 에이전트 운영사(Operator)와 개별 에이전트 인스턴스를 등록·검증하고, 모든 요청을 암호학적으로 서명하게 한다.
2. **범위 제한 위임**: 사용자가 금액·머천트·카테고리·기간·빈도 한도를 가진 Mandate를 발급하고 언제든 철회할 수 있다.
3. **거래 시점 검증**: 머천트가 SDK 한 줄(또는 API 1회 호출)로 "누가(에이전트) / 누구를 대신해(사용자) / 무엇을 할 권한이 있는지(Mandate)"를 검증한다.
4. **위험 기반 Human-in-the-loop**: 한도 초과·이상 징후 시 사용자 패스키 승인(Step-up)으로 전환한다.
5. **증빙·감사**: 의도(Intent)→장바구니(Cart)→결제(Payment)까지 서명된 영수증 체인을 남겨 분쟁 증거로 쓴다.
6. **상호운용성**: OAuth 2.1, RFC 9421(HTTP Message Signatures), SD-JWT, AP2/ACP/Visa·Mastercard 에이전트 프로그램과 매핑 가능해야 한다.

### 비목표 (v1)
- 자체 결제 네트워크/카드 발급 — PSP·카드 네트워크 토큰을 **중개**만 한다(PCI 범위 최소화).
- 에이전트 자체 개발(LLM 오케스트레이션) — 우리는 인프라다.
- 에이전트 행동 품질(추천 적절성) 판단.

## 4. 주요 이해관계자

| 역할 | 설명 | AgentPass에서 얻는 것 |
|---|---|---|
| User (Principal) | 구매 권한을 위임하는 사람 | 비밀번호 공유 없이 안전한 위임, 실시간 철회, 사용 내역 |
| Agent Operator | 에이전트를 만드는 회사/개발자 | 머천트에서 "신뢰받는 에이전트"로 통과, 표준 SDK |
| Agent Instance | 실제 요청을 보내는 개별 에이전트 실행체 | 단명(short-lived) 키·토큰 |
| Merchant (RP) | 상품을 파는 쪽, 검증자 | 좋은 봇/나쁜 봇 구분, 위임 증빙, 차지백 방어 |
| PSP / Issuer | 결제대행·카드사 | 에이전트 거래 식별 신호, 위임 증빙 |

## 5. 단계별 계획 (Phase)

| Phase | 기간(가정) | 산출물 | 디렉토리 |
|---|---|---|---|
| P0. 리서치 | 1주 | 시장·표준 조사 | `docs/01-research/` |
| P1. 요구사항 | 1주 | PRD, 유스케이스, 기능/비기능 요구사항 | `docs/02-requirements/` |
| P2. 아키텍처 | 2주 | 시스템 아키텍처, 데이터 모델, 시퀀스, 위협 모델 | `docs/03-architecture/` |

이번 작업 범위: **P0 ~ P5** (설계 완료 + 설계 검증용 프로토타입).

## 6. 마일스톤 & 완료 기준

- **M1 설계 동결**: ADR 전부 Accepted, 위협 모델의 High 위협 전부 대응책 매핑.
- **M2 프로토타입 검증**: 아래 시나리오가 자동 테스트로 통과
  - 정상 위임 구매 성공
  - 한도 초과 → Step-up 요구
  - 철회된 Mandate 거부
  - 다른 에이전트 키로 토큰 재사용(탈취) 거부
  - 요청 본문 변조 거부
  - 재전송(replay) 거부
  - 영수증 체인 변조 탐지
- **M3 파일럿 KPI**: 머천트 연동 ≤ 1일, 검증 API p99 ≤ 50ms, 오탐(정상 에이전트 차단) < 0.1%.

## 7. 주요 의사결정 요약 (상세: `docs/adr/`)

| # | 결정 | 이유(요약) |
|---|---|---|
| ADR-0001 | 신규 프로토콜 대신 **OAuth 2.1 + 확장 프로파일** | MCP 인가 스펙·기존 IdP와 상호운용, 학습비용 최소 |
| ADR-0002 | 에이전트 요청 인증 = **HTTP Message Signatures (RFC 9421)**, Web Bot Auth 호환 | CDN/WAF 레벨 검증 가능, 업계 수렴 방향 |
| ADR-0003 | Mandate = **서명된 JWT(SD-JWT 선택적 공개) + 에이전트 키 바인딩(cnf)** | 오프라인 검증, 개인정보 최소 공개, 탈취 시 무용 |
| ADR-0004 | 카드번호 미보관, **PSP/네트워크 토큰 중개** | PCI DSS 범위 축소, 규제 리스크 최소화 |
| ADR-0005 | **위험 등급 기반 Step-up** (패스키/CIBA) | UX와 보안의 균형 |
| ADR-0006 | **단명 토큰(5분) + Status List + Webhook** 철회 | 즉시 철회와 오프라인 검증의 절충 |
| ADR-0007 | **해시 체인 서명 영수증**으로 감사·분쟁 증빙 | 부인 방지, 외부 검증 가능 |
| ADR-0008 | 기술 스택: 코어 Go / SDK TypeScript·Python / PostgreSQL / KMS | 성능·생태계·운영 |
| ADR-0009 | 저장소: 기존 repo 내 독립 디렉토리로 시작 | 신규 repo 생성 권한 부재(403) — 분리 가능 구조 유지 |

## 8. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| 카드 네트워크/빅테크가 자체 표준으로 시장 장악 | 높음 | 경쟁 아닌 **어댑터 계층** 포지셔닝 (AP2/ACP/Visa TAP/MC Agent Pay 매핑) |
| 머천트 연동 동기 부족 | 높음 | CDN/WAF 플러그인, 차지백 보호 프로그램, 무료 검증 티어 |
| 규제(전자금융거래법, PSD3/SCA)에서 "사전 위임"의 인정 여부 | 중간 | Mandate를 SCA 위임 증빙 형태로 설계, 규제 샌드박스 활용 |
| 프롬프트 인젝션으로 에이전트가 정당한 Mandate 내에서 악용 | 중간 | Mandate 범위 최소화, 머천트 허용목록, 이상 탐지, 고위험 Step-up |
| 키 관리 실패(에이전트 키 유출) | 높음 | 단명 인스턴스 키, 운영사 키는 HSM/KMS, 즉시 폐기 |
